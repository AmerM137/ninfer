1 · Objective and ground rules

Deliver ninfer.exe and ninfer-serve.exe built from this tree on 64-bit Windows, executing the full product surface from the same artifacts, compiled for sm_120a as on Linux. The port is host-platform work only: no target identity, kernel schedule, artifact format, or serving schema changes. Platform branches are confined to a small file list and guarded by _WIN32; no feature is dropped.

Two platform differences are accepted and documented rather than hidden: TLS trust roots (system CA bundle on Linux, Windows certificate store via Schannel) and a reduced curl feature set (no compressed transfer encodings, HTTP/1.1 only). Neither affects media bytes. Docker stays Linux-only; WSL, TCC mode, multi-GPU, and installers are out of scope. Published performance numbers remain Linux results — Windows gets its own measured row at the end.

2 · Dependency strategy

Both dependencies are provisioned locally and discovered through pkg-config on both platforms — no vcpkg, no CMake platform branch. The unmodified tree configured on Windows on the first attempt; all five version gates passed.

DependencyChoiceWhy
FFmpeg BtbN n6.1.2 win64 LGPL shared prebuilt at C:\libs\ffmpeg-n6.1.2 Shared, because the mingw-built static archives cannot be linked by MSVC — only a C ABI crosses the DLL boundary, and the decode path never crosses the CRT heap or file handles. LGPL keeps the binaries distributable. n6.1.2 specifically matches the Linux reference (Ubuntu 24.04 / FFmpeg 6.1 / swscale 7): a swscale rounding difference would change decoded pixels, then vision tokens, then generated text — a silent cross-platform divergence dressed up as a port bug.
libcurl 8.21.0 built from source: static, Schannel TLS, at C:\libs\curl With Schannel it has zero external dependencies and builds in a minute. Static means nothing extra to deploy; Schannel means HTTPS trust comes from the Windows certificate store with no CA-bundle discovery problem.

vcpkg was evaluated and rejected: it added a multi-hour FFmpeg source build and a registry baseline while providing nothing the manual pkg-config path doesn't, and two of its defaults (dynamic triplet, Schannel-backed curl) contradicted assumptions an earlier draft depended on.

Deployment set: five DLLs beside every binary that loads FFmpeg — avcodec-60, avformat-60, avutil-58, swscale-7, swresample-4. swresample never appears on a link line (it is a private dependency of avformat behind the DLL boundary) but is required at load time. CMake now stages all five into build/apps/ and build/tests/ at configure time.

3 · What changed in the tree

The whole port is ~800 inserted lines across 36 files, four of them new (console_unicode.{h,cpp}, hostexec.py, and the containment regression test). By area:

Build system

  • /utf-8, /bigobj, and /Zc:preprocessor on both the plain cl path and nvcc's host path (CCCL #errors on the traditional preprocessor); NOMINMAX + WIN32_LEAN_AND_MEAN globally.
  • UTF8PROC_STATIC on ninfer_text — without it MSVC decorates utf8proc symbols as dllimport and rejects the definitions (C2491).
  • ws2_32 linked explicitly for ninfer-serve; curl's .pc already carries the Winsock set for media acquisition.
  • Op-test FP model: /fp:strict on MSVC. The decision was probed, not assumed — disassembly of a*b+c on cl 19.51 shows no FMA contraction even under /arch:AVX2 /fp:precise; only /fp:fast or /fp:contract would introduce it. The flag pins that contract against either creeping in.
  • FFmpeg DLL staging into apps/ and tests/ (configure-time copy).

Artifact reader — the central item

MappedFile in src/artifact/reader.cpp gained a Win32 implementation behind the same class. Two handles on the same file: a plain handle backing CreateFileMappingW/MapViewOfFile for the JSON directory and small resources, and a FILE_FLAG_NO_BUFFERING handle for the 4096-byte-aligned direct reads that carry every tensor payload — the Windows equivalent of the Linux O_DIRECT contract.

  • Direct reads are positional: the offset travels in an OVERLAPPED structure on a synchronous handle, so no file pointer mutates and read_direct stays honestly const. The 4096-byte pre-checks are kept verbatim; they match the NO_BUFFERING sector rules.
  • At open, the volume's logical sector size is probed via GetFileInformationByHandleEx(FileStorageInfo). Sector > 4096 (or an unsupported file system) degrades to buffered reads — a correct, slower load, logged once, never a failure.
  • Limit checks re-expressed against LONGLONG/DWORD (off_t/ssize_t don't exist under MSVC); DWORD is the tighter byte-count bound and is enforced.
  • The load-bearing subtlety — a trailing partial sector at EOF must return a short count, not an error, exactly as O_DIRECT pread does — was verified empirically on the target volume before trusting it (§6).

Pinned staging

PinnedHostBuffer keeps its API; internally it is now an explicitly 4096-byte aligned allocation (_aligned_malloc / posix_memalign) pinned with cudaHostRegister, released with cudaHostUnregister plus the original aligned free. This makes the direct-I/O alignment guarantee hold by construction on both platforms instead of relying on the driver returning page-aligned memory. ratified Plan decision 9.4 is now recorded as the broad option: every consumer on both platforms gets the one alignment guarantee, and the accepted cost (page-granular pinning on small per-request ingress buffers) pulls the arena into the Linux regression pass.

Python tooling

New shared helper tools/bench/hostexec.py, wired into run_serve_corpus.py, run_serve_concurrency.py, run_ninfer_bench_matrix.py, and serve_thinking_preservation.py:

  • binary_path() resolves build-tree binaries with the .exe suffix on Windows (single-config generator assumed — Ninja, the documented choice).
  • Servers start with CREATE_NEW_PROCESS_GROUP and stop via request_stop() — CTRL_BREAK_EVENT on Windows instead of Popen.terminate(), which is TerminateProcess and would skip the console handler, losing the request log's final records. SIGTERM on POSIX, unchanged.
  • format_command() renders reproduction command lines with list2cmdline on Windows instead of POSIX shlex quoting.
  • migrate_v1_to_v2.py fails fast on Windows with a "Linux-only" parser error (its durable-rename path needs os.O_DIRECTORY; v1 is a dead format).

README gained the Windows requirements and a "Building on Windows" section (provisioning recipe, CMAKE_PREFIX_PATH configure line, native-tools-prompt requirement, DLL staging); AGENTS.md gained Windows in the product contract and a Windows toolchain row.

4 · The one real blocker: NVFP4 TMA kernels vs. MSVC

Both NVFP4 TMA translation units failed under MSVC with C2719 — and the root cause is NVIDIA's own header. cuda.h declares CUtensorMap as alignas(128), the kernels take four of them by value as a __grid_constant__ parameter, and nvcc's generated host launch stub re-declares that parameter by value. GCC copies an over-aligned by-value parameter into an aligned slot; MSVC refuses any formal parameter aligned beyond the stack-slot guarantee. Skipping the target was not an option: five caller families depend on it, including the largest NVFP4 GEMMs in the tree.

Resolution — opaque byte parameter. The descriptors travel as Nvfp4W4a4TmaDescriptorBytes, a uint8_t[sizeof(...)] wrapper with alignment 1, reinterpreted inside the kernel. This keeps __grid_constant__ and constant-bank residency, and touches only the parameter declaration — no per-launch H2D upload, no host-compiler swap. The known risk (nvcc placing the alignment-1 wrapper at an offset that violates CUtensorMap's own 128-byte contract, which would fail as a silent wrong-address TMA load) is guarded by a device-side check that asserts 128-byte alignment — the type's bound, deliberately stricter than the driver's documented 64 — and traps loudly before any load.

This is kernel source that Linux also compiles, so the fix pulls NVFP4 correctness into the Linux regression pass. On Windows the guard has been exercised live: the TMA route runs at exactly its admission gate (tokens = 1024) in the op tests, all five caller families pass, and the guard has never trapped.

5 · Review findings and fixes

A full review of the port diff (plus empirical probes on the target machine) produced nine fixes, all landed and re-verified. The two that mattered most:

GetConsoleMode(handle, nullptr) crashes on a real consolefixed

The interactive-stderr probe passed nullptr for the mode output. Verified with MSVC-built probes: on a real console handle this raises an access violation — and with redirected stderr the call fails before the dereference, so the crash appears only in interactive use and evades every piped test. Until the fix, any console run of ninfer.exe died at the first progress line. Fix: a real DWORD output.

CreateFileMappingW failure checked against the wrong sentinelfixed

That API reports failure as NULL, not INVALID_HANDLE_VALUE. A real mapping failure slipped past the check and surfaced one call later with a masking error code, and cleanup called CloseHandle(NULL). Fix: nullptr checks and sentinel for the mapping handle.

Frontend test died as an opaque 0xc0000409fixed

Not a port bug: the test reads the official Qwen3.6-27B HF tokenizer files from a hardcoded path in the maintainer's Linux home directory. With no top-level catch, the miss reached std::terminate, which MSVC reports as fail-fast with all buffered output discarded. Fixes: the path is overridable via NINFER_QWEN3_6_27B_HF, absence skips with code 77 and a message, and main now catches and prints. The test skips cleanly until the three small JSON files are provisioned.

The remaining six: WSAStartup failure throws a typed error instead of std::exit(1); the TMA trap's diagnostic printf is gated to one thread per block; the /fp:strict comment records the actual disassembly probe; the request-log test now byte-asserts LF-only output; CMake stages the FFmpeg DLLs (they had been hand-copied); and the media-root containment change — *relative.begin() == ".." instead of a native-string prefix test that falsely rejected real entries named like ..hidden — gained a dedicated regression test (tests/test_media_acquire_path.cpp) covering accept and escape cases on both platforms. That containment change is Linux-visible and is recommended for its own commit.

6 · Verification evidence

Empirical probes (MSVC-built, target machine)

  • Trailing short read at EOF under FILE_FLAG_NO_BUFFERING — the one place the port could silently corrupt a load: on C: (NTFS, 512-byte logical sectors) a 4096-byte positional read whose range ends 1808 bytes past the last sector boundary returns TRUE with bytes_read = 1808 and correct content, matching O_DIRECT pread. Reads at/past EOF fail with ERROR_HANDLE_EOF, which the materializer never issues.
  • FP contraction: none under any /fp:precise configuration on cl 19.51, including /arch:AVX2 (§3).
  • GetConsoleMode null behavior: crash confirmed, fix shape confirmed (§5).

This closes the Windows half of Phase 3.
  • Serve driven by the tooling: serve_thinking_preservation.py drives ten requests (Chat Completions + Responses API, tool calls, checkpoint restores) end to end through ninfer-serve.exe. Nine pass every assertion; the tenth is the parity question below.

One smoke assertion diverges — a parity question, not a tooling defectLinux-side

The Responses-API continuation (previous_response_id, thinking inherited) takes the append_frontier reuse path where the smoke expects restore_response_checkpoint; all chat-side checkpoint assertions pass. The path chosen is a deterministic function of whether the parent's 16 greedy output tokens re-tokenize identically across the response boundary in the re-rendered continuation prompt — i.e., this is the plan-§6 cross-platform greedy-parity question surfacing through a smoke. The Linux run settles it: if Linux generates the same 16 tokens and still restores from the checkpoint, this is a real port divergence to chase; otherwise the smoke's expectation is content-coupled.

Operational reality worth keeping: the plan's GPU-contention risk materialized immediately — a resident llama-server held 27 of 32 GB VRAM at review time and had to be closed before GPU verification could run. Benchmark runs need the same discipline.
