# Qwen3.8-27B DFlash2 支持临时执行计划

> 状态：路线已确认，代码实现尚未开始。
>
> 目标版本：现行 `.ninfer` v2。
>
> 生命周期：本文是跨阶段工作的临时路线记录，不是并行的 artifact、模型或 Engine 权威，也不
> 加入公共文档索引。实现稳定后，应将最终合同分别回写到现有 active maintainer references、
> CLI/serving 文档和 model card，并删除本文。

## 1. 目标与范围

目标是在现有 Qwen3.8-27B Engine 路径中加入完整 DFlash2 speculative backend，并满足：

1. `qwen3.8-27b/groupwise-int` 和 `qwen3.8-27b/nvfp4` 两个重新转换的 artifact 都内嵌
   DFlash2 权重；
2. MTP 与 DFlash2 权重共存于同一个 artifact，但 Engine 启动时只选择并 materialize 一个
   speculative backend；
3. 已发布、不含 DFlash2 的两个旧 artifact 继续支持现有 Text、Vision、MTP、prefix reuse、
   CLI、serving 和 measurement 行为；
4. 只有显式选择 DFlash2 且 artifact 缺少完整 DFlash2 bundle 时才报能力缺失错误；
5. DFlash2 通过同一个公共 `.ninfer` Engine 路径执行，并覆盖一至八个启动固定 active
   requests、compact decode batch、prefix/continuation、CUDA Graph 和最终性能验证；
6. DFlash2 最终支持 Qwen3.8-27B 的 image/video Vision prompt，并复用已在 35B DFlash 中
   修正的多模态 attachment 和位置语义。

本工作明确不依赖、不等待也不修改未生效的 v3 迁移草案。当前任务只扩展 v2。

本计划不预先实现新 Op，也不把 SGLang 或 vLLM 变成 NInfer 的执行或正确性路径。两者只用于
核对 checkpoint mapping、算法边界和状态顺序；最终语义、实现、oracle 和性能证据由 NInfer
自己拥有。

## 2. 已冻结的产品决策

### 2.1 Backend 身份

公共 C++ 枚举、CLI、日志和统计使用独立的 DFlash2 身份：

```text
SpeculativeBackend::DFlash2
--spec dflash2
```

现有 35B-A3B `SpeculativeBackend::DFlash` 保持原义。DFlash 与 DFlash2 可以共享 family-owned
生命周期机制，但不得在产品诊断和统计中互相冒充。

一个 Engine 实例在启动时冻结为 `none`、`mtp`、`dflash` 或 `dflash2` 之一，不在请求间或请求
内切换 backend，也不同时构造两个 speculative module 的权重 view、状态、workspace 或 Graph。

### 2.2 Draft 几何

首个支持合同只接受 artifact 原生 block size 8：

```text
query block = 1 anchor + 7 mask positions
draft_tokens = 7
verify width = 8
```

不把 SGLang 的 `speculative_num_draft_tokens=8` 直接解释成 NInfer 的七个 draft 之外再增加一位。
扩大到其他 block width 需要单独的模型有效性、acceptance 和 Graph 性能证据。

### 2.3 Proposal head

DFlash2 支持现有两种启动固定 proposal-head route：

- `full`：复用主模型完整 `text/output_head`；
- `optimized`：复用现有 `text/draft_head` 和 `text/draft_head_token_ids`。

两条 route 都需要输出每个 proposal position 的 top-16，而不是现有 DFlash 的单个 argmax。
optimized route 必须先把 shortlist row 映射为完整 token id，再访问完整词表上的 selector
codebook。Shortlist 可以改变 draft/acceptance，但 target verification 仍保证最终输出语义。

### 2.4 Vision

DFlash2 的完成定义包含 Vision prompt。Text eager 闭环可以作为中间里程碑，但不能作为最终
产品完成条件。Vision 路径在 Text decoder 已融合视觉 embedding 后捕获相同的目标层 hidden
features，并沿用 35B DFlash 已支持的 Vision/DFlash 共存合同；若后续事实推翻这一 attachment
语义，必须显式修改本计划和产品合同。

## 4. v2 Artifact 兼容合同

### 4.1 Core 与可选 companion bundle

现行 v2 合同放宽为：

```text
(model_id, weights_id)
├── fixed core inventory and storage semantics
└── zero or more target-declared, all-or-none optional companion bundles
```

本任务只引入一个这样的 bundle：Qwen3.8-27B DFlash2。它不改变 core Text、MTP、Vision、
frontend、已有 proposal head 或任何现有对象的语义。

以下变化仍要求新的 `weights_id`：

- 修改、删除或重新解释 core object；
- 改变 core fusion、numeric format 或 storage layout 合同；
- 使同名 core object 的 payload 不再按原合同解码。

仅追加一个不影响 core 的、target reference 明确注册的可选 companion bundle，不要求新
`weights_id`，也不要求新 framing revision。

### 4.2 有效 inventory

对于现有两个 Qwen3.8 identity，v2 binder 只接受：

1. 精确 legacy core inventory；或
2. 同一 legacy core inventory 加完整 DFlash2 bundle。

规则为：

- 没有任何 `dflash2/` object：合法旧 artifact；
- bundle sentinel 存在：逐个绑定并验证完整 DFlash2 descriptor；
- sentinel 不存在但出现其他 `dflash2/` object：`Binder::finish()` 以未消费对象拒绝；
- sentinel 存在但任一对象缺失或 descriptor 错误：按不完整 bundle 拒绝；
- 未注册的其他额外对象仍被拒绝。

Generic v2 Reader、prefix、JSON root/object schema、payload offset 和 layout registries 均不改变。
Binder 只需增加无副作用的对象存在查询；bundle 的完整性和意义继续由 Qwen3.8 target binder
拥有。

### 4.3 选择与 materialization

| Artifact | `none` | `mtp` | `dflash2` |
|---|---|---|---|
| legacy core-only | 正常 | 正常 | 启动时明确报告 DFlash2 bundle 缺失 |
| core + DFlash2 | 正常，DFlash2 validate-only | 正常，仅 MTP resident | 正常，仅 DFlash2 resident |

补充不变量：

- 新 artifact 中未选 DFlash2 时仍验证完整 descriptor，但不进行 DFlash2 H2D；
- 选择 DFlash2 时 MTP tensors 只验证、不上传，也不分配 MTP KV/state/Graph；
- optimized proposal head 只在选中 `ProposalHead::Optimized` 时上传；
- qwen3.6-27b profiles 选择 DFlash2 时报告 target capability 不支持，而不是伪装成缺少
  Qwen3.8 bundle；
- 35B-A3B 的 artifact 合同不变；其 DFlash runtime 已允许与 Vision 同时启用。

### 4.4 Converter 输出策略

新 converter 只有一种当前输出：完整 core 加完整 DFlash2 bundle。可选性只服务运行时读取已
发布旧 artifact，不增加 `--without-dflash2`、legacy converter 或第二条产品生成路径。

```text
qwen3.8-27b/groupwise-int  -> identity unchanged, recipe sidecar may become v2
qwen3.8-27b/nvfp4          -> identity unchanged, recipe sidecar may become v2
```

`recipe_id`、source revision 和转换报告不是运行时身份。当前两个旧 artifact 及 sidecar 在重新
转换前移动到明确、稳定的 compatibility 路径；不得用 glob、mtime 或“latest”名称选择它们。

## 5. DFlash2 Artifact Inventory 与量化路线

### 5.1 计划对象边界

对象名不携带 format spelling。建议 namespace 为：

```text
dflash2/feature_projection
dflash2/context_norm
dflash2/layers/{l}/input_norm
dflash2/layers/{l}/attention_conv/base_kernel
dflash2/layers/{l}/attention_conv/kernel_projection
dflash2/layers/{l}/attention/query_key_value
dflash2/layers/{l}/attention/query_norm
dflash2/layers/{l}/attention/key_norm
dflash2/layers/{l}/attention/output
dflash2/layers/{l}/post_attention_norm
dflash2/layers/{l}/mlp_conv/base_kernel
dflash2/layers/{l}/mlp_conv/kernel_projection
dflash2/layers/{l}/mlp/gate_up
dflash2/layers/{l}/mlp/down
dflash2/final_norm
dflash2/candidate_selector/hidden_projection
dflash2/candidate_selector/predecessor_codebook
dflash2/candidate_selector/successor_codebook
```

每层将 source Q/K/V 合并为 `[6144,5120]` parent，将 gate/up 合并为 `[34816,5120]`
parent。按上述边界，baseline bundle 是六个 global objects 加 `5 x 12` layer objects，共 66 个
tensor objects。若最终选择需要独立 persistent auxiliary scalar 的 physical format，这些 scalar
也属于同一个全有或全无 bundle，最终计数由冻结后的 inventory 为准。

### 5.2 第一条闭环量化候选

第一条高保真、可尽快闭合 Engine 的候选不是最终发布结论：

- feature、attention、MLP 和 dynamic-convolution projection matrices：`W8G32_F16S`；
- norms 和 dynamic-convolution base kernels：`BF16`；
- selector codebooks：先保留 `BF16`；
- selector hidden projection：作为 W8/BF16 小矩阵在 Phase 2 比较；
- embedding、full head 和 optimized head：继续 alias core objects，不复制 payload。

该候选预计增加约 `2.02 GiB` persistent tensor payload。两个 artifact 可以先共享相同 DFlash2
physical allocation，就像现有 MTP；这不妨碍后续根据证据为 groupwise-int 和 nvfp4 选择不同
的 DFlash2 formats。

### 5.3 最终量化选择

最终方案必须比较，而不能只根据文件大小决定：

1. W8 contractions + BF16 codebooks 基线；
2. 适用矩阵的 Q4/Q5 组合；
3. W8 或更低精度 codebook 及其直接 gather/decode route；
4. 有真实 activation calibration 和完整 divisor 合同支持时的 NVFP4 候选。

当前 NVFP4 format 依赖匹配的 input divisor。不能把 BF16 DFlash2 source 无依据地直接包装成
NVFP4，也不能默认为 divisor `1`。若不建立校准合同，nvfp4 主 artifact 中的 DFlash2 module
继续使用 W8/BF16 是合法且清晰的混合方案。

量化质量以 end-to-end acceptance、tokens/round 和输出吞吐评估。Greedy 最终输出正确性仍由
target verification 保证；概率采样还要求 proposal `q` 与 accept/correction 消费的 `q` 完全
一致，不能用“最终文本看起来合理”替代验证。

## 7. 状态和执行结构

### 7.1 Persistent state

DFlash2 五层全部使用 window 2048 的 local cyclic K/V：

```text
5 layers x K/V x 8 heads x 128 x 2048 x 2 bytes = 40 MiB / StateImage
```

它没有 DFlash Full layer，因此：

- 不创建 DFlash Full paged-KV pool；
- 不申请 `backend_kv_pages`；
- context frontier 仍需独立记录，以证明 local cyclic state 对应哪个绝对前缀；
- assistant-boundary、Host replica、fork/copy 和 long-distance restore 继续通过 StateImage
  transaction 管理这 40 MiB local state；
- 不能为了复用当前 DFlash 代码而伪造一个零用途 full-cache row。

### 7.2 Decode round

稳定 round 的逻辑顺序为：

```text
commit previous accepted target features to DFlash2 local context
    -> prepare [anchor, mask x 7]
    -> main embedding alias
    -> five DFlash2 layers
       (dynamic conv -> non-causal SWA -> dynamic conv
        -> dynamic conv -> MLP -> dynamic conv)
    -> final norm
    -> full/optimized head top-16 per draft position
    -> selector lattice and one coherent path
    -> retain selected path's sparse proposal q
    -> target verify width 8 and capture five target feature layers
    -> greedy or sparse-q accept/correction
    -> publish exact licensed prefix and retain pending context for next round
```

与现有 DFlash 一样，DFlash2 context 只提交 target 已确认的 prefix，不提交未验证 draft 的 query
K/V。Partial terminal 和 cancellation 使用 shared pending transaction，不引入每轮 40 MiB undo。

## 8. Op 工作边界

### 8.1 可复用或扩展的现有能力

- target hidden feature sink；
- `prepare_masked_block`；
- embedding、RMSNorm、RoPE；
- feature/context projection、QKV projection、MLP 和 residual composition；
- symmetric non-causal sliding-window attention；
- cyclic KV append和StateImage transfer；
- target verification、GDN record/replay 和 accepted-hidden selection；
- proposal-head alias/remap、pending publication 和 CUDA Graph infrastructure。

Sliding-window attention 需要把已资格范围扩展到 window 2048 和 DFlash2 的真实调用 shapes；这
是现有 Op domain/route 扩展，不是第二个模型私有 attention Op。

### 8.2 新增语义能力

预计至少需要以下 closed Ops 或对现有 Op family 的实质扩展；最终拆分在相应 contract 设计时
冻结：

1. 两 tap、group size 16、按 request block 断开的 dynamic grouped convolution；
2. full/optimized output projection后的稳定 top-16 token/logit selection；
3. rank-256 codebook edge scoring和greedy/stochastic selector path walk；
4. 接收 sparse candidate ids + FP32 `q` rows 的 speculative accept/correction；
5. 若 codebook 最终量化，直接消费其 registered format 的随机行 gather/decode route；
6. 现有 linear families 对相关 `[5120,*]`、`T=7xB|8xB` 形状和选定 formats 的高性能 route。

第 4 项是概率正确性边界。当前 `speculative_accept_greedy_drafts` 把 proposal 视为 one-hot，不能
用于 DFlash2 stochastic path。Selector path 与 rejection 必须消费同一组 FP32 proposal scores/
probabilities；把 selector scores 中途降为 BF16 可能改变路径和 `q`，不得作为未经资格验证的
实现细节。

### Phase 1：v2 合同与精确 storage map

### Phase 2：Converter、Binder 与新 Artifact

工作：

- 保存当前两份真实旧 artifact及sidecar；

退出条件：

- source 81 tensors 恰好全部被消费，且没有未声明 source；
- 新 artifacts 的 identity 不变，bundle 完整；
- legacy `none`/MTP load plan 正常，legacy DFlash2 只在选择时明确失败；
- 新 artifact 的 `none`/MTP route 没有 DFlash2 H2D；
- converter-side代表性decode证明每种stored tensor符合其format oracle。

Phase 2 的 artifact 可以使用高保真 baseline allocation。最终发布 allocation 仍由 Phase 6 的完整
acceptance/throughput 证据决定，必要时重新转换，而不是把早期候选永久冻结。

### Phase 3：DFlash2 数学与 Op contracts

工作：

- 定义 target feature capture 点、context K/V、非因果可见集和block边界；
- 定义dynamic convolution完整公式和prepare/finish中间值的可观察性；
- 定义top-16 tie、selector edge、path sampling、RNG domain和FP32 `q`；
- 定义 sparse proposal rejection/correction及target sampling filters/penalties的交互；
- 为每个闭合 Op 编写独立 FP32/FP64 或 exact oracle。

退出条件：Op contracts 足以独立实现和验证，不再依赖 SGLang/vLLM 的执行结果作为 oracle；
Program-owned lifecycle 与 Op-owned数学没有交叉所有权。

### Phase 4：Op 实现与资格验证

工作：

- 实现并验证新增 Ops 和已有 Op domain 扩展；
- 覆盖真实 shapes、`B=1..8`、Graph capture/replay和greedy/stochastic分支；
- 为选定的 groupwise/NVFP4 artifact formats 补齐直接消费 route；
- 只对可能影响当前设计的实际热点做性能比较。

退出条件：所有生产 route 直接通过同一个独立 oracle；性能足以进入完整 Engine，而不是只证明
某个 microbenchmark 好看。

### Phase 5：Eager Engine 闭环

工作：

- public option、startup validation、immutable model view和conditional residency；
- DFlash2 local state、workspace和round-state布局；
- Text/Vision prefill feature capture及context construction；
- seven-draft proposal、selector、target verify和sparse-q accept；
- initial proposal、steady rounds、ordinary capacity tail、partial terminal和cancellation；
- prefix/continuation、assistant boundary、Host replica和长于2048 token的restore；
- mixed-length compact batches和`B=1..8`。

退出条件：

- DFlash2 target verification、accept/correction和状态提交分别通过其独立数学/事务 oracle；不同
  数值执行路径之间不要求greedy token逐项一致；
- stochastic route 满足同一 target 分布合同；
- target GDN、continuation hidden、DFlash2 local context及所有frontier在accept/reject/terminal后
  一致；
- image/video prompts完成同一闭环；
- none/MTP、35B DFlash和两个Qwen3.8 core route无回归。

### Phase 6：CUDA Graph、量化定稿与产品收尾

- 为 exact `B=1..8`、K=7 和必要 frontier tiers 完成 Graph capture/replay；

## 10. 最终验证矩阵

### 10.1 Artifact 与加载

- legacy groupwise：none、MTP成功，DFlash2按选择失败；
- legacy nvfp4：none、MTP成功，DFlash2按选择失败；
- new groupwise：none、MTP、DFlash2成功，inactive bundle不resident；
- new nvfp4：none、MTP、DFlash2成功，inactive bundle不resident；
- partial/unknown bundle：无条件拒绝；
- full/optimized proposal head：各自只materialize依赖闭包。

### 10.2 数值与状态

- dynamic convolution、top-16、selector和sparse rejection独立oracle；
- real-shape quantized-weight decode和代表性model intermediates；
- greedy exact target output；
- stochastic分布、penalty/filter和RNG domain；
- all-accept、first-reject、middle-reject、zero/short output和partial terminal；
- context跨2048 cyclic边界、prefix fork、Host restore和continuation；
- CUDA Graph与eager通过同一语义准则。

### 10.3 产品与性能

- Text、image和video；
- CLI、OpenAI和Anthropic serving；
- concurrency `1..8`、mixed request lengths和bounded FIFO；
- full/optimized head；
- 与ordinary和现有MTP的acceptance、tokens/round、decode tok/s、load bytes和HBM residency比较；
- 未选择DFlash2时的性能和内存回归检查。

## 11. 已知高风险点与控制门

| Risk | Control |
|---|---|
| v2旧规则把完整inventory绑定到weights_id | Phase 1先正式引入core + exact optional bundle合同 |
| partial bundle被当作legacy | sentinel、逐项require和`Binder::finish()`三重闭合 |
| 复用one-hot accept导致概率错误 | 独立sparse-q accept contract和distribution oracle |
| selector path与rejection看到不同`q` | 同一FP32 q rows贯穿proposal与accept |
| all-local DFlash2被迫申请Full paged pool | resource/state布局显式支持zero full layers |
| 量化提高kernel速度但降低acceptance | 用end-to-end accepted tok/s决定最终allocation |
| optimized shortlist映射后索引错codebook | top-16先映射为global token id，再做selector gather |
| Vision多模态路径未完整接入 | 复用35B已验证的capture/position合同，Phase 5仍作为完成门 |
| 为DFlash2复制Program或调度器 | 只新增module-private proposal数学，复用family transaction |
| 过早做kernel profiling | 完整Engine先闭环，按真实热点逐层归因 |
